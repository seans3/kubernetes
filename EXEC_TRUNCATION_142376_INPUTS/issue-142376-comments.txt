---- aojea 2026-10-01T10:42:14Z
IIUIC the process in the pod has already finished and written all its output, and then containerd/crio starts closing the connection. 
Depending on the transport SPDY or WebSocket the symptoms are different, but in both cases what you see is a cascade of errors triggered because the server side closed the underlying TCP socket while data was still buffered (because the client didn't drained it yet)

This is a graceful termination / half-close problem across multiple proxied hops. If you see the different legs involved you'll see why this is not something we can fix with one drive-by PR:

```
[kubectl (client-go)]
   │  WebSocket (v5.channel.k8s.io) or SPDY (v4.channel.k8s.io)
   ▼
[kube-apiserver]  proxy, or WebSocket→SPDY translator
   │  WebSocket (v5, 1.36+ ExtendWebSocketsToKubelet) or SPDY (v4)
   ▼
[kubelet]  proxy, or WebSocket→SPDY translator
   │  SPDY (v4.channel.k8s.io)
   ▼
[CRI streaming server (containerd / CRI-O, vendoring k8s.io/cri-streaming)]
   │  pipes
   ▼
[process in the container]
```

Because this require multiple components (apiserver, kubelet, containerd/crio) we need to clearly define the rollout to handle the compatibility. This also has a risk of allowing ddos scenarios by holding resources open. 

I am inclined to ask for a KEP that defines the protocol change, the per-component rollout and the compatibility matrix. KEP-4006 (https://github.com/kubernetes/enhancements/tree/master/keps/sig-api-machinery/4006-transition-spdy-to-websockets) is a good reference.

The issue also has a workaround (keep the process alive after its last write, or verify sizes/checksums on the receiving side). And a reminder: exec, attach, cp and port-forward are listed under "Troubleshooting and Debugging Commands" for a reason. Kubernetes has proper APIs for exposing and moving workload data (Services, LoadBalancers, volumes); building production data paths on the debugging streaming APIs is not recommended





---- semx 2026-10-01T14:22:12Z
Thanks, that matches what we see. You're right on both points: 15 minutes is more than the wait needs, and a change across every hop needs a KEP with a rollout plan. In short, from measurements on a real cluster (details below):

- 500 ms cuts even a fast client on a LAN, and 30 s already cuts a 256 KiB/s reader; on SPDY every cut run exits 0.
- The wait does add something: a finished session can be held without a process for up to 15 minutes, which is cheaper than holding one with `sleep`, and no metric shows it while it waits. The ceiling doesn't change: a client that stops reading can already hold a session for 4h, because wsstream lets the idle timeout override write deadlines. That's older than this PR; the fix is #142596.
- So the KEP should bound the wait on progress and make it visible (a gauge of waiting sessions, a counter of expiries). After the command exits the server writes nothing more, so progress there means the socket draining: visible on Linux (TIOCOUTQ or TCP_INFO), elsewhere only through the client's pings, which needs a floor on the rate.
- On skew: in every mix I measured, each run the new client reported as failed had lost output, and against an all-old server it exits 0 normally (40 of 40). It can still be worse in one case, which follows from the code and didn't show up in my runs: an old server that loses only the status frame after the last byte. The old client calls that success, the new one an error; the KEP should decide between a typed error and a release note.

I'll write the KEP with KEP-4006 as the model if SIG Node and SIG API Machinery agree. Would you be up for reviewing it?

<details><summary>Measurements</summary>

**How long does an honest client need?** I made the bound settable on one node and ran 16 MiB through `kubectl exec` with the reader capped, 5 runs per cell. Complete runs, out of 5, for WebSocket / SPDY:

| bound | 16 MiB/s | 1 MiB/s | 256 KiB/s |
|---|---|---|---|
| 15 min | 5 / 5 | 5 / 5 | 5 / 5 |
| 30 s | 5 / 5 | 5 / 5 | 2 / 0 |
| 5 s | 5 / 5 | 2 / 0 | 0 / 0 |
| 500 ms | 0 / 0 | 0 / 0 | 0 / 0 |

Every SPDY run that came back short exited 0, and the only thing on stderr was a "Copying stdin failed" line from my stdin feeder, which complete runs print too. That's the original bug. The wait is roughly what's buffered between the runtime and the client (about 13 MiB on the SPDY path, going by the slow-reader runs) divided by the read rate: 0.6–3 s for the fast reader, up to 15 s at 1 MiB/s, up to 61 s at 256 KiB/s. So 500 ms truncates even a fast client on a LAN.

**What can a client hold today?** With `pods/exec`, far more than 15 minutes. With `streamingConnectionIdleTimeout` and containerd's `stream_idle_timeout` both set to 1m on a node, `kubectl exec -- sleep 300` ran the full 300 s over WebSocket and over SPDY. A raw WebSocket client that sends nothing wasn't cut at 1m either: the WebSocket-to-SPDY translator has its own idle timeout, hard-coded to 4h (`defaultIdleConnectionTimeout`), and the kubelet setting doesn't reach it. That also means our doc comment saying a shorter idle timeout ends the wait sooner was wrong for the translator.

While checking that, I found a worse hole, and it predates this PR. On the WebSocket path, wsstream moves the connection's deadline to the idle timeout on every frame it writes, so no write deadline set before a write holds: not the one `finish` sets, and not the 10s `writeErrorDeadline` either. A client that stops reading while the command is still writing keeps the session for the idle timeout, 4h, with or without this change, and longer if it keeps sending something. In a unit test, a write with a 300 ms deadline returned after the 4s idle timeout. Both doc comments now say what actually bounds those writes (fce8f6619e), and the fix for wsstream, with that test, is #142596. It's a bug on its own, and it's what the writes in `finish` need to be bounded on WebSocket.

200 sessions held on one node, added to baseline:

| | raw WebSocket client, `sleep 86400`, sends nothing (today) | raw WebSocket client, `echo hi`, never closes (this PR) |
|---|---|---|
| apiserver | +400 fds, +604 goroutines | +400 fds, +601 goroutines |
| kubelet | +400 fds, +4001 goroutines | +199 fds, +401 goroutines |
| containerd | +1001 fds | none, that leg is already closed |
| processes in the container | +200 | 0 |

The finished sessions in the right column hold no process and so cost the client less than the left one.
