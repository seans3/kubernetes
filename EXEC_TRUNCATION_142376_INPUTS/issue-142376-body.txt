TITLE: Exec drops end of stdout when client reads slowly
STATE: open
AUTHOR: knoppiks
CREATED: 2026-09-24T08:15:17Z

### What happened?

I tried to take a backup of a pod's data using `kubectl exec`. When inspecting file sizes the files seemed not to be the same. After some testing and experiments, I found the issue to occur only when the client reads slower than the (in-pod) process writes (to stdout). Only the end of the stream was missing, the beginning was intact. `kubectl exec` often exited with 0, with nothing on stderr. So the truncated result could not be told apart from a complete one. `kubectl cp` fails the same way when the client is behind a slow link with `error: unexpected EOF` (copying to a fast local disk did not fail). The error occurred using the older SPDY transport as well as WebSockets.

**kind v1.37.0, two nodes, kubectl v1.37.0; pod writes 32 MiB, client reads at 1MiB/s**

path | truncated reads | # of those with exit 0 + empty stderr
-- | -- | --
kubectl exec, WebSocket (default) | 3/5 | 0
kubectl exec, SPDY | 5/5 | 5
crictl exec on the node, same reader | 5/5 | 5
crictl exec on the node, reader not throttled | 0/5 |  
kubectl exec, process sleeps 45 s after its last write | 0/1 |  

* crictl exec on the node, where only the CRI streaming server is involved, already truncates
* packet captures have shown the kubelet passes everything it received, so bytes are lost at the streaming server & apiserver -> client connection

### What did you expect to happen?

Everything the remote (in-pod) process wrote should have reached the client, or the client should exit with a non-zero exit code.

### How can we reproduce it (as minimally and precisely as possible)?

I let a coding agent reproduce the error in various ways (k3s, kind, crictl, k8s versions from 1.30 to 1.37), full measurements, per-hop packet captures and scripts: https://github.com/knoppiks/k8s-exec-truncation-repro

I ran the reproduction myself, on multiple nodes. With the folowing script
<details open>
<summary>Script to reproduce</summary>

```bash
cat <<'EOF' | kind create cluster --name trunc --config -
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes: [{role: control-plane}, {role: worker}]
EOF
kubectl run payload --image=alpine:3.22 --restart=Never \
  --overrides='{"spec":{"nodeName":"trunc-worker"}}' -- sleep infinity
kubectl wait --for=condition=Ready pod/payload --timeout=120s

# The container writes exactly 32 MiB (33554432 bytes) and exits 0.
PAYLOAD='head -c 33554432 /dev/zero'

# A reader that consumes 1 MiB per second and prints how many bytes it got.
slow_count() {
  total=0
  while n=$(head -c 1048576 | wc -c) && [ "$n" -gt 0 ]; do
    total=$((total + n)); sleep 1
  done
  echo "got=$total"
}

# 1) kubectl exec through the apiserver: WebSocket (default), then SPDY.
for ws in true false; do
  echo -n "kubectl exec, websockets=$ws: "
  KUBECTL_REMOTE_COMMAND_WEBSOCKETS=$ws kubectl exec payload -- sh -c "$PAYLOAD" | slow_count
  echo "  kubectl exit code: ${PIPESTATUS[0]}"
done

# 2) The same reader on the node, reading crictl exec directly: only the CRI
#    streaming server is in the path. No kubelet, apiserver or network.
id=$(docker exec trunc-worker crictl ps --name payload -q)
echo -n "crictl exec on the node: "
docker exec trunc-worker bash -c "$(declare -f slow_count)
  crictl exec $id sh -c '$PAYLOAD' | slow_count
  echo \"  crictl exit code: \${PIPESTATUS[0]}\""

# Control: keep the process alive until the reader has caught up.
echo -n "kubectl exec, 'sleep 45' after the last write: "
kubectl exec payload -- sh -c "$PAYLOAD; sleep 45" | slow_count
```
</details>
