#### What this PR does / why we need it:

`kubectl exec` and `attach` lose the end of the output when the client reads more slowly than the command writes and is also sending input (#142376). The server writes the status and closes the connection at once; the client's next frame then makes the kernel reset the connection and drop what is still in the send buffer. Over SPDY, client-go then sees an empty status and reports success.

The change:

- The CRI streaming server (`k8s.io/cri-streaming`) and the WebSocket translator no longer close first. They send the status, signal the end (SPDY: close the output streams; WebSocket: a close frame, new `wsstream.Conn.CloseWrite`), and wait for the client to close, bounded by the request context and 15 minutes.
- client-go treats an empty status stream on v4/v5 as an error (`connection closed before the command's status was received`) instead of success.

Behaviour change: a client that neither closes nor answers the close frame now holds the session for up to 15 minutes after the command exits (the old code returned at once).

Tested with unit tests that reproduce the loss on the old code, and on a real multi-node cluster with containerd, CRI-O and Windows; results in https://github.com/kubernetes/kubernetes/pull/142461#issuecomment-5920263856.
